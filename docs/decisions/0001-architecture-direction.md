# 架构方向与阶段边界

状态：建议方向，具体技术选型待工程骨架变更确定。2026-10-28。

## 已确认的约束

三人协作，先形成规范再开发；服务对象为培训机构，学生端与教师端共同完成练习闭环。需要隔离机构资料，追溯作答与题目版本，支持外部模型和向量检索。仓库公开，实际学习数据私有。

## 建议方向

采用模块化单体业务服务，加独立任务工作进程；前端以响应式 Web 为首发入口。模块按身份与机构、题目与材料、分析、练习与反馈、学习记录组织；模型、文件、消息和检索通过适配层接入。

候选技术延续早期方案：Vue 3/TypeScript、Python/FastAPI、PostgreSQL/pgvector、Redis/任务队列及容器化。这里只记录候选，不锁版本、不安装依赖，也不声称已验证部署。

## 取舍

| 方向 | 考虑的替代方案 | 当前建议及代价 |
| --- | --- | --- |
| 模块化单体 | 多个业务微服务 | 三人团队先减少部署与分布式事务成本；保留模块边界，扩展时仍需拆分设计 |
| 单关系库加向量扩展 | 关系库加独立向量服务 | 候选方案减少存储同步环节；大规模召回性能必须测量，不能据此保证容量 |
| 异步分析与导出 | 同步等待全部模型结果 | 用户可查询任务与重试；需投入任务幂等、进度及恢复设计 |
| 已审核题库推荐 | 自动生成新题 | 可追溯来源与答案；早期覆盖受题库质量限制，候选不足需如实提示 |
| 规则统计加教师复核 | 复杂知识追踪模型 | 易解释、可重算；不能据简单正确率宣称精确掌握概率 |

## 后续决策方式

工程骨架变更给出备选比较、团队熟悉度、部署条件和最小验证结果后冻结技术栈。模型供应商通过固定评测与成本预算选择；登录方案、部署地区、题库授权与数据留存需要单独结论。

初期不因“正式互联网产品”而同时引入全部基础设施。任何新增工具要有明确职责、维护负责人及检查方法。
