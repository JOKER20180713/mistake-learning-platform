# 一次变更的执行流程

当前规范阶段仅执行文档适用步骤。进入开发后沿用本流程，检查工具以检查清单登记为准。

1. 明确一个可独立验收的目标，检查基线规约和待决项。只解决本次依赖的待决问题，不扩大到整个产品所有问题。
2. 新建变更目录，先写 proposal：问题、范围、边界、依赖与验收方式。
3. 写 design：方案、候选、代价、权限、数据、兼容与失败处理。没有技术影响时明确说明，不凑选型。
4. 写增量 spec：每条 Requirement 有 Scenario，给定角色和数据，操作明确，结果可断言；覆盖该能力真实存在的失败与边界。
5. 写 tasks：按依赖拆分，列出规约编号、维护人、检查和证据；不预先勾选未执行事项。
6. 检查四文件一致性后在独立分支工作。业务规则发生变化先同步规约，已有授权范围内的实现细节自主处理。
7. 执行当前适用的检查，记录失败及修复；修改权限、状态和去重逻辑必须有能发现其失效的用例。
8. 提交 PR，按模板附实际验证及影响；非作者评审；有例外则登记。
9. 合并后更新基线，保存版本和证据，再归档变更；功能上线另走发布流程。

完成判断引用评审规范。任何自动化工具生成的“通过”都必须能定位到输入、版本和真实运行结果。
