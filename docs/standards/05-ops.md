# 部署运维规范

维护人：司浩鸣。当前没有部署环境，以下为上线目标，所有演练状态见检查清单。

| 编号 | 要求 | 检查方法 |
| --- | --- | --- |
| OPS-01 | 依赖锁定，多阶段构建，仅运行产物进入镜像；镜像按提交号/摘要标识 | 同一锁文件与构建输入可复现；部署记录能定位确切摘要 |
| OPS-02 | 开发、测试、生产的数据和机密分离；经过测试的同一镜像跨环境提升 | 生产发布不另编译一份未经测试产物，环境只改变配置 |
| OPS-03 | `/health/live` 仅检测进程；`/health/ready` 检测 API 必需数据库，未就绪不接流量 | 数据库故障时就绪失败，存活不因模型断网而失败；健康响应不含内部地址 |
| OPS-04 | 模型、检索、队列、导出分别记录能力状态；不可用时执行各自契约，不伪装成功 | 停用一个依赖，其他可用能力继续工作，失败有明确业务结果 |
| OPS-05 | 收到停止信号后停止接收新任务；在途处理有截止时间，未完成任务可恢复领取 | 任务执行中重启，恢复后不得丢任务或重复扣配额/新增记录 |
| OPS-06 | 单行 JSON 日志至少含时间、级别、模块、request_id、事件、结果、耗时；异步增加 job_id 和原始 request_id | 从一次上传串到任务及导出；不出现正文、凭据或签名 URL |
| OPS-07 | 观测请求量、错误率、p95、队列等待、依赖可用率和模型用量；告警有阈值、责任人和动作 | 人为制造一次故障，验证告警通知到负责人且附排查入口 |
| OPS-08 | 发布记录代码、镜像、配置、迁移与提示词版本；数据库变化先兼容扩展再切换，删除最后执行 | 旧应用可在新结构上运行；演练旧版本回退而不删除新数据 |
| OPS-09 | 备份包含数据库、原图/PDF 与题库版本清单；恢复后应用删除清单，避免已删资料复活 | 从备份恢复到独立环境，核对业务与删除记录，而非只检查备份文件存在 |
| OPS-10 | 按机构和用户限制写入与高成本任务；限流在受理前执行并返回 429/Retry-After | 超额请求不继续排队；重放已接受的幂等请求不再次消耗额度 |
| OPS-11 | 发布、配置变化、回退及故障复盘归档，保留操作者、版本、时间、验证与结果 | 按版本可找到完整记录；未演练不能声称具备回退能力 |

## 首期性能与恢复目标

这些是待验证的初始验收目标，测量环境与测试数据必须随报告记录，不能作为已达到的服务承诺。

- 非模型 JSON 读取：20 并发、稳定 60 秒且至少 200 次请求，服务端端到端 p95 ≤ 500 ms，预期成功请求错误数为 0；不含浏览器首次静态资源下载。
- 异步任务受理：同等负载下 p95 ≤ 1 s，不把排队与模型完成时间混入此指标。
- 单次外部调用与重试上限见 AI 规范；任务排队超过 5 分钟标记延迟，超过 10 分钟仍未执行则失败并释放预留额度，不无界等待。
- 停机等待上限 30 秒；不适合在 30 秒内完成的任务保存可恢复状态，禁止强行标成功。
- 首期备份目标为每日一次、保留 30 天，恢复点目标 RPO ≤ 24 小时、恢复时间目标 RTO ≤ 4 小时。对外承诺前必须完成演练并确认部署地区及客户留存条款。
- 基础故障告警：5 分钟内非预期 5xx 比例 > 5% 且请求数 ≥ 20，或队列最老任务 > 5 分钟；司浩鸣牵头处理，模型问题交周潇洋协作。

API 实例和工作进程的就绪条件分别设置。任务受理检查可靠持久化与调度能力；已提交事务但投递失败由 Outbox 恢复。数据库故障期间不得返回 202 假装已接收。

发布动作按 [发布流程](../workflows/release.md) 执行。回滚应用不是回滚全部数据；不可逆迁移先有前向修复与恢复方案。
