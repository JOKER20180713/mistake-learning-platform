# 规范基线的组织设计

## 采用方案

在独立 Git 仓库维护原生 Markdown。README 提供入口与真实阶段状态，AGENTS 指向全局约束和适用规范，八份规范保存规则，工作流程保存操作顺序，OpenSpec 风格目录保存业务基线和变更材料。

产品、权限、状态、API 和数据定义各有唯一维护来源；其他文件引用而不重复定义。规则编号用于检查追溯，检查台账区分当前文档检查和未来程序检查。

## 候选与取舍

- 未采用把全部规则塞入单个 AGENTS：阅读负担大且重复易冲突；代价是需要维护索引与链接。
- 未直接复制课程工程目录和技术栈：示例事实不等于本项目事实；代价是需要单独完成真实技术选择。
- 未在本次安装 OpenSpec CLI、创建 CI 脚本或应用骨架：符合先规范后代码的阶段；代价是程序门禁尚不存在，必须明确记录。
- 未把三位实名直接猜成 GitHub 账号：保留职责表，账号映射待提供后再配置。

## 检查设计

运行补丁格式检查；对所有 Markdown 检查本地文件链接、围栏和替换字符；检查八类规则编号及业务场景编号唯一；检查文件扩展名和公开内容范围。人工核对角色、状态、HTTP/业务码、幂等及反馈统计的一致性。

验证结果只对应文档，本次不运行模型、数据库或业务测试。证据记录实际步骤及未完成事项，远端推送后读取仓库状态核验公开性与提交。
